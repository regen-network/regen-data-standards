# Schema

[LinkML](https://linkml.io/) semantic schemas for Regen Network framework.

These schemas define the structure and semantics for credit class and project metadata in the Regen Network ecosystem. They provide a standardized way to describe:

- **Credit Class Information**: Metadata for carbon and biodiversity credit classes, including protocols, methodologies, eligible activities, and environment types
- **Project Information**: Geospatial and descriptive data for projects enrolled in a given credit class
- **Impact Tracking**: Primary impacts and co-benefits associated with projects
- **Taxonomies**: Controlled vocabularies for activities, environment types, and impact types

The schemas are designed to be converted to RDF/JSON-LD formats for semantic web integration and SPARQL querying.

> **Note**: Current on-chain datasets may not fully reflect this schema. The schemas in this repository (and the playground folder) represent the latest up-to-date versions of all Regen Network datasets in a format consistent with current Regen Data Standards.

## Requirements

[Install LinkML](https://linkml.io/linkml/intro/install.html) to use the helper and generator commands for interacting with LinkML schemas and data. Use the versions pinned in the repository's `requirements.txt`, which need Python 3.10 or later:

```shell
pip install -r requirements.txt
```

Every schema module needs a URI `id` (for example `https://framework.regen.network/schema/Claim`); `make lint` rejects a bare name.

## Structure

- LinkML schemas are created in `schema/src`.
- Create separate schema files for each logical schema class and `import` into the root `schemas.yaml` file.
- Generated markdown from schemas:
  ```shell
  make gen-doc
  ```
- Generate linkml enums for taxonomy terms:
  ```shell
  make gen-taxonomy
  ```

## Published schema artifacts

The schema is published as versioned artifacts generated from `src/schema.yaml` and its imports,
for the version `src/schema.yaml` declares (`version:`). Each version is in `versions/<version>/`:

| File | Generated by | Use |
|---|---|---|
| `context.jsonld` | `gen-jsonld-context --xsd-anyuri-as-iri`, corrected (below) | JSON-LD context for documents of this version |
| `json-schema.json` | `gen-json-schema --include-range-class-descendants`, with a `$id` unique to the version | JSON Schema; the entry point for a class is `#/$defs/<class>` |
| `shacl.ttl` | `gen-shacl`, serialized canonically | SHACL shapes; the shape for a class has the class IRI and targets it |
| `linkml.yaml` | `gen-linkml --mergeimports` | The schema with every import merged, including `linkml:types`, so generation and validation need no import lookups |
| `hierarchy.ttl` | `scripts/gen-hierarchy.py`, serialized canonically | `rdfs:subClassOf` and `rdfs:subPropertyOf` triples of the `rfs:` classes and slots. Load it with the data: instances carry only their most specific class, and with it the open `Claim` and `Evaluation` shapes apply to every claim type and kind of evaluation |
| `examples/` | Copies of `examples/*.jsonld` with this version's context | Valid examples, and invalid ones the manifest says what they violate |
| `records/` | Copies of `examples/records/*.jsonld` with this version's context | The records the examples cite by IRI: `evidence.jsonld` holds every `Evidence` record, as one JSON-LD `@graph` |

[`versions/manifest.json`](versions/manifest.json) maps each version to:

- `source`: the source revision, as the git tree hash of `schema/src` (`git rev-parse
  <commit>:schema/src` prints it for any commit with the same files, so it survives a squash merge),
  the git blob hash of each module, which pins the imported base and shared modules, and the commit
  it was taken from, where known;
- `generators`: the versions of the packages that shape the artifacts: `linkml`, `linkml-runtime`,
  `rdflib` (which serializes `shacl.ttl`) and `PyYAML` (which writes `linkml.yaml`), all pinned in
  `requirements.txt`;
- `files`: each artifact's path and SHA-256, and the JSON Schema's `$id`;
- `entryPoints`: every concrete class that specializes `Claim`, and `Evidence`, whose records are
  documents of their own, each with its class IRI, JSON Schema location and SHACL shape;
- `examples`: each example's entry point, whether it is valid, and, if not, the only slots it may
  violate;
- `records`: each records file, the class of its records and its SHA-256.

`latest` names the highest version. The first version, `0.1.0`, is the schema with the base Claim,
Evaluation, Evidence and C06 claim modules
([#85](https://github.com/regen-network/regen-data-standards/pull/85),
[#87](https://github.com/regen-network/regen-data-standards/pull/87),
[#90](https://github.com/regen-network/regen-data-standards/pull/90)) and the existing credit class
and project modules.

### Commands

```shell
make gen-schema-artifacts    # generate the current version's artifacts, examples and manifest entry
make check-schema-artifacts  # check the bundle offline (below)
make check-schema-artifacts BASE=origin/main  # also check that versions published there are unchanged
make gen-context             # regenerate one artifact while iterating
make gen-json-schema         #   (the manifest entry is only updated by
make gen-shacl               #    gen-schema-artifacts)
make check-claim-examples    # check the examples and invalid documents with the published validators
```

`check-schema-artifacts` blocks network access, then checks that:

- every file the manifest lists exists and has its SHA-256, and every entry point exists in the JSON
  Schema and SHACL shapes;
- every example of every version is accepted by both validators, or, if invalid, rejected by both
  and only on the slots the manifest names. SHACL checks each example as a graph store holds it:
  with the version's `hierarchy.ttl` and, unless it is an `Evidence` record, with the version's
  `records/`. Every record is checked too. `c06-mvp-claim-domain-invalid.jsonld` has the base Claim
  fields of `c06-mvp-claim.jsonld` and fails only the C06 constraint on `practices`;
- for the current version, `src/` is the recorded source and regenerating every artifact gives the
  same bytes;
- a version that records a commit has, at that commit, the recorded `schema/src` tree, when the
  commit is in the local history. CI's shallow checkout usually lacks older commits; the check then
  reports that it cannot compare, and `bundle` compared them when it recorded the commit.

CI runs it on every pull request with `BASE` set to the base branch.

### Versions

A published version never changes: when definitions change, declare a new version in
`src/schema.yaml` and run `make gen-schema-artifacts`, which adds it to the manifest and leaves the
others as they are. Until a version is published, it can be regenerated. A version can also be
generated from a checkout of an earlier source:

```shell
git -C .. archive <commit> schema | tar -x -C <dir>
python3 scripts/schema-artifacts.py generate --source <dir>/schema --version <version>
python3 scripts/schema-artifacts.py bundle --source <dir>/schema --version <version> --commit <commit>
```

`bundle` records `--commit` as a full SHA, and stops without writing anything unless that commit's
`schema/src` has the tree hash of `<dir>/schema/src`, so the manifest never names a commit its source
did not come from.

### Validating a document

The entry point is the class of the document's root node (its `@type`). Validate:

- with SHACL: the RDF graph of the JSON-LD document, parsed with the version's context, against
  `shacl.ttl`, together with `hierarchy.ttl` and the `Evidence` records the document cites by IRI
  (the `source` of each `hasEvidenceCitation`): the shapes require each cited IRI to be an
  `rfs:Evidence`. An `Evidence` record is
  validated on its own. Keep lexical forms as written: `assertedAt` must keep its `Z`;
- with JSON Schema: the document's LinkML data form against `json-schema.json#/$defs/<class>`:
  the document with its JSON-LD keywords (`@context`, `@type`) removed, except that a selector's
  `@type` is written back as its `selectorType` (`"FragmentSelector"` becomes
  `"selectorType": "oa:FragmentSelector"`), which the JSON Schema uses to tell the selector classes
  apart.

Imported definitions are not separate targets: they are checked as values reached from the root.
Neither validation needs a network lookup: the context is inline, and the shapes, hierarchy and JSON
Schema are self-contained.

A validator that holds several versions keeps them apart:

- each version's JSON Schema has its own `$id`,
  `https://framework.regen.network/schema/versions/<version>/json-schema.json`, so they can be
  registered together. The `$id` identifies the schema; nothing is served at that URL;
- SHACL shapes are identified by their class IRI (`rfs:Claim`, …), which is the same in every
  version, so load each version's `shacl.ttl` into a graph of its own.

### Generator limitations

LinkML 1.11.1, checked with pyshacl 0.40.1:

- **The generated JSON-LD context does not give the same RDF as the Turtle output**, so
  `scripts/schema-artifacts.py` corrects it, and every example and playground fixture is checked
  against its Turtle:
  - a slot name that classes map differently keeps one term, so the slot of the other classes gets
    a type-scoped context (JSON-LD 1.1) on its class: `File.description` (`dcterms:description`),
    `File.name` (`dcterms:title`) and `ReferenceId.identifier` (`rfs:identifier`);
  - enum terms are strings; they get `"@type": "@vocab"` and a scoped context mapping each value to
    its `meaning`. An enum without meanings (BT01's) stays a string, as in the Turtle output. An
    enum where only some values have a meaning cannot be expressed: JSON-LD would make every value
    an IRI, while the Turtle output keeps a value without a meaning a string. The script refuses to
    generate the context for one, so give every value a meaning (as `ImpactType`'s `UNKNOWN` has,
    `rfs:UnknownImpact`);
  - `uri` and `uriorcurie` values are `xsd:anyURI` literals unless the context is generated with
    `--xsd-anyuri-as-iri`;
  - nested objects need an explicit `@type`, which `scripts/claim-examples.py` adds when it builds a
    document.
- **Class `rules` are not translated to SHACL** ([linkml/linkml#2464](https://github.com/linkml/linkml/issues/2464)),
  so a constraint written as a rule is enforced by the JSON Schema only. In this schema, those are
  four: a `RequirementEvaluation` whose `requirementOutcome` is `UNDETERMINED` states a
  `rationale`; a `RequirementAssessmentResult` that is `APPLICABLE` states a `requirementOutcome`,
  and one that is `NOT_APPLICABLE` states none; an `EvidenceSupportResult` whose `evidentialStance`
  is `NO_BEARING` has no `evidenceSufficiency`. Each has an invalid example marked
  `# shacl: not enforced`.
- **A `pattern` on an identifier slot is not checked by SHACL**, which cannot match a pattern
  against the IRI of a node. `Evidence.id` must have no fragment (`^[^#]*$`); the JSON Schema
  enforces it, and its invalid example is marked `# shacl: not enforced`.
- **Class-level `any_of` is dropped by `gen-shacl`.** A slot-level `any_of` over enums is expressed
  in JSON Schema and SHACL, but the generated context leaves its values as strings, so SHACL rejects
  valid values, and `linkml-convert` fails on it.
- **A JSON-LD number in a `decimal` slot fails SHACL** (`Value is not Literal with datatype
  xsd:decimal`); a string such as `"12.5"` passes.
- **A prefix must be declared where LinkML uses it.** The Turtle output writes a CURIE whose prefix
  the root schema does not declare as an IRI with that scheme (`<geo:asWKT>`), and LinkML drops an
  enum `meaning` written as a full IRI without a declared prefix, so the value becomes a string
  (SDG). `src/schema.yaml` declares `geo:` and `sdgs:` for this.
- **`gen-shacl` output order varies between runs.** It is generated with `PYTHONHASHSEED=0` and
  serialized canonically, so it can be compared byte for byte.
- **A typed node of a subclass fails `sh:class`** for its superclass unless the validator is given
  the class hierarchy, which is why each version publishes `hierarchy.ttl`.
- **A `uriorcurie` slot cannot be narrowed to an enum in a subclass**: the generated Python model of
  the base class rejects the value.

## Playground

Datasets are provided inside `schema/data/playground/{Credit-Class}/{LinkML-Class}-*.yaml` files. All datasets are managed in github as YAML files as this is more lightweight and easier to manage (as the standardized source for LinkML datasets) than storing JSON-LD or TTL files in version control.

There is a designated make task (`gen-rdf`) for validating and generating RDF data in formats besides YAML. This creates `.ttl` and `.jsonld` files for each dataset: the Turtle with `linkml-convert`, the JSON-LD with the published context of the current version, and it checks that both give the same graph (numbers compared by value). To run the script, use the following command:

```shell
make gen-rdf
```

## Claim examples and checks

The base Claim is described in [`docs/claim-base.md`](../docs/claim-base.md).

| File | Shows |
|---|---|
| [`generic-claim.jsonld`](examples/generic-claim.jsonld) | A self-attested stewardship claim with an inline context. It has no credit class, impact or attestation. |
| [`generic-claim-revision.jsonld`](examples/generic-claim-revision.jsonld) | An immutable revision that names the earlier version by a labelled placeholder ClaimIRI. |
| [`claim.INVALID-*.yaml`](examples/) | Documents the base must reject: a candidate without a claimant, a claim without a statement, a language name instead of a language tag, review state, the Claim's own hash/IRI, an empty claimant set, a date-only, local-offset or `Z` assertion time, a bare-IRI subject, inlined evidence, a citation without a source, and domain fields on the base. |

The JSON-LD files are generated from the playground fixtures in
[`data/playground/Claim/`](data/playground/Claim/), which `gen-rdf` validates, by
`make gen-claim-examples`. CI runs `make check-claim-examples`, which runs the published validators
of the current schema version (`versions/<version>/`) on every document:

- the JSON Schema (`json-schema.json`, errors reported as `linkml-validate` reports them) over the
  authored YAML;
- the SHACL shapes (`shacl.ttl`, run with pyshacl) over the RDF graph of the authored JSON-LD and
  over the Turtle that `gen-rdf` writes for the fixture, which `update-graph` publishes. Both are
  parsed without rdflib's literal normalization, so lexical forms are checked as written. The
  generated shapes are used unchanged.
- SHACL over each example retyped as a claim type defined outside this repository, with a field of
  its own and its `rdfs:subClassOf rfs:Claim` triple. The open `Claim` shape must accept it, and
  must reject it without `assertedBy`.

The check reads that Turtle, so `gen-rdf` must run first, as it does in CI. It fails if an example
is stale, if its JSON-LD graph is not isomorphic to the fixture's published Turtle, if either
validator rejects a valid example or its published Turtle, or if either accepts an invalid one.
JSON Schema must reject each invalid document with the error named on its first line.

The inline context is the published context of the current schema version, generated from
`schema.yaml` with `gen-jsonld-context --xsd-anyuri-as-iri`, so `uri` and `uriorcurie` terms (`url`,
`wasRevisionOf`, `references`) map to `@type: @id` and their values are IRI nodes, as in Turtle. It is
corrected so that it gives the same RDF as the Turtle output: enum terms map each value to its
`meaning`, so a claimant's `"COMMUNITY"` becomes `rfs:Community`, not a string, and a slot name that
classes map differently, such as `File`'s `description` in `ProjectPost.yaml` (`dcterms:description`),
is redefined in a type-scoped context on its class. Nested objects carry `@type`. The corrections and
the other generator limitations are listed under [Generator limitations](#generator-limitations).

### Timestamps

`assertedAt` is written in UTC with whole seconds and the offset `+00:00`, for example
`2026-05-02T07:30:00+00:00`. RDF literals are compared by their exact text, so the same instant
written two ways (`Z` and `+00:00`, or `…:00` and `…:00.0`) would give the same assertion two
identities, and one spelling is required. XSD 1.1 names these redundancies
([lexical mappings][XSD-LEX]); its canonical representation for a zero offset is `Z`
([timezone canonical mapping][XSD-TZ]), but canonical representations "are not required for schema
processing itself" ([definition and note][XSD-CANON]). The base requires `+00:00` because LinkML and
rdflib write that form: LinkML objects rewrite `Z` as `+00:00` when they load data, and rdflib does
the same unless `NORMALIZE_LITERALS` is off. So the authored fixtures and the RDF that `gen-rdf`
publishes both conform, with no rewriting step. A tool that writes `Z` by default, such as
JavaScript's `Date.prototype.toISOString()`, must write `+00:00` instead. A pattern enforces the
format in both JSON Schema and SHACL, so `Z` is rejected
([example](examples/claim.INVALID-z-suffix-assertion-time.yaml)), and so is a local offset such as
`+02:00` ([example](examples/claim.INVALID-local-offset-assertion-time.yaml)). This applies to
timestamps only: date-only values elsewhere stay dates and are not shifted to UTC.

Because LinkML and rdflib would turn a rejected `Z` into an accepted `+00:00`, tools must check the
text as written. So CI validates the authored files with `linkml-validate` rather than with
`linkml-convert --validate`, and `check-claim-examples` parses RDF with literal normalization off. How
the identity recipe treats timestamp literals is decided in
[claims#1](https://github.com/regen-network/claims/issues/1).

[XSD-LEX]: https://www.w3.org/TR/xmlschema11-2/#rf-lexicalMappings-datetime
[XSD-CANON]: https://www.w3.org/TR/xmlschema11-2/#dt-canonical-representation
[XSD-TZ]: https://www.w3.org/TR/xmlschema11-2/#f-tzCanFragMap

## SPARQL Integration

If you are running a SPARQL endpoint, you can use the following command to push datasets via a GRAPH_STORE API to update datasets to a live SPARQL store. This adds all `.ttl` files to the graph. Override the `GRAPH_STORE_URL` env var:

```shell
export GRAPH_STORE_URL=http://localhost:7878/store
make update-graph
```
